--------------------------------------------------------------------------------
FINDING: AgentExecutor removed in langchain>=1.0.0
--------------------------------------------------------------------------------
Error:
  cannot import name 'AgentExecutor' from 'langchain.agents'

Cause:
  LangChain 1.x removed the legacy AgentExecutor class. The modern replacement
  is langgraph.prebuilt.create_react_agent, which provides a stateful ReAct
  agent graph with built-in tool-calling loop, streaming, and step callbacks.
  This is the recommended path from LangChain docs as of 2025.

Decision:
  Use langgraph.prebuilt.create_react_agent throughout agent.py.
  Do NOT use langchain.agents.AgentExecutor — removed, not backported.

TEST 4 — Runtime: MultiServerMCPClient context manager removed
--------------------------------------------------------------------------------
Error at runtime:
  NotImplementedError: As of langchain-mcp-adapters 0.1.0,
  MultiServerMCPClient cannot be used as a context manager (async with ...).

Cause:
  langchain-mcp-adapters 0.2.2 removed the __aenter__/__aexit__ methods from
  MultiServerMCPClient. The async context manager pattern we used was valid in
  0.0.x but was deliberately removed in 0.1.0+.

Fix applied in agent.py:
  Before (broken):
    async with MultiServerMCPClient({...}) as client:
        tools = client.get_tools()

  After (correct for >=0.1.0):
    client = MultiServerMCPClient({...})
    tools = await client.get_tools()

Reference: langchain-mcp-adapters changelog, 0.1.0 release notes.

  After:  from langchain.agents import create_agent

OLLAMA MODEL SELECTION
--------------------------------------------------------------------------------
Minimum requirement: model must support tool/function calling natively.
  llama3 (base)    — does NOT support tool calling, will ignore tool schemas
  llama3.1         — SUPPORTS tool calling (Meta's official function-calling model)
  llama3.2         — SUPPORTS tool calling (smaller, faster)
  qwen2.5          — SUPPORTS tool calling (strong multilingual + reasoning)
  mistral-nemo     — SUPPORTS tool calling

Default in agent.py: llama3.2
Override via env:   OLLAMA_MODEL=llama3.1 python3 agent/agent.py

Rationale for llama3.2 as default (revised after benchmark):
  llama3.1 (8B, 4.9GB): ~3-8 tokens/sec on CPU — 5-10 min per query.
  llama3.2 (3B, 2.0GB): ~15-25 tokens/sec on CPU — under 60 sec per query.
  Both support tool calling. llama3.2 is the practical default for CPU-only
  machines. llama3.1 remains available via OLLAMA_MODEL env var.

Recommendation for markers:
  ollama pull llama3.2   # default — fast on CPU
  ollama pull llama3.1   # higher quality if GPU available

--------------------------------------------------------------------------------
ARCHITECTURE EVOLUTION — single-agent ReAct → multi-agent planner-executor
--------------------------------------------------------------------------------
Branch: feature/mcp         — single-agent ReAct (langchain.agents.create_agent)
Branch: feature/multi-agent — multi-agent LangGraph StateGraph (this branch)

Problem observed in feature/mcp:
  llama3.2 was required to simultaneously (a) choose between 4 tools,
  (b) generate correct SQL / MongoDB filter parameters, and (c) write the final
  answer — all in a single ReAct loop. The model frequently wrote tool calls
  as plain-text JSON instead of using the function-call mechanism, requiring a
  brittle post-hoc recovery pass.

Root cause (documented in ReAct paper, Yao et al. 2022 arXiv:2210.03629):
  Small LLMs (<7B) exhibit degraded performance when the action space is large
  relative to model capacity. The model conflates the routing decision with
  parameter generation and synthesis.

Solution — planner-executor-synthesizer architecture:

  [Planner Node]
    ChatOllama(format="json") constrains generation to valid JSON output.
    The routing task (classify question → which store) is a simpler, isolated
    sub-problem than the combined route+params+answer task of a single agent.
    Returns: {"route": "warehouse|geodata|semantic|multi", "intents": {...}}

  [Executor Nodes] (warehouse_node, geo_node, semantic_node)
    Each node handles ONE tool. The LLM only generates parameters for a tool
    it is already known to be calling — routing is already solved by the planner.
    SQL generation, MongoDB filter generation, and semantic queries are
    separated into specialist nodes with focused, short system prompts.

  [Synthesizer Node]
    Receives clean summaries of all tool results (via _summarise_for_synthesizer).
    Its only task is writing a coherent English answer from structured data.

  Routes:
    warehouse → Warehouse  → Synthesizer
    geodata   → Geo        → Synthesizer
    semantic  → Semantic   → Synthesizer
    multi     → Warehouse  → Semantic → Synthesizer

Key technical decisions:
  - format="json" on planner LLM eliminates free-text tool-call failure mode
  - Annotated[list, operator.add] accumulates results across nodes in state
  - One SQL retry with error context in warehouse_node
  - _summarise_for_synthesizer() strips raw JSON; synthesizer sees clean data

Pattern reference:
  LangGraph supervisor pattern: https://langchain-ai.github.io/langgraph/
  Yao et al. "ReAct: Synergizing Reasoning and Acting in Language Models" (2022)
  arXiv: 2210.03629
